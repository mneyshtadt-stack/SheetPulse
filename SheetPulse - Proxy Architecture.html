SheetPulse — Proxy Architecture

How SheetPulse went from a public "anyone with the link" Google Sheet to a private backend that only opens for one signed-in Google account — every component, every URL, and the exact steps that built it.

Why any of thisWhat problem this solves

Stage one: SheetPulse fetched data from Google Sheets' "Publish to web" CSV export. That's a public URL — anyone who ever saw it (browser history, a screenshot, a shared link) could pull the raw numbers directly, forever, with no login and no way to revoke it short of un-publishing.

Stage two: the sheets were unpublished, and SheetPulse instead asked a small private server (the "proxy") for the data, accepting an answer only if the request carried a secret token and came from SheetPulse's own web address. That closed the public link, but the token itself still had to live inside this static page's own JavaScript for the browser to send it — anyone who read the page's source could find it and call the proxy directly.

Stage three (current): the static token is gone. SheetPulse now requires signing in with Google (SSO), and every request instead carries the viewer's own Google ID token — a short-lived, digitally signed credential the proxy independently re-verifies against Google's own public keys on every single request, checking both its signature and that its email matches the one allowed account. There is no longer a standing secret anywhere in this page's source for a reader to find and reuse.

What's left: the Web OAuth Client ID embedded in the page is meant to be public (Google's own design for browser sign-in flows) — it identifies the app, not a person, and can't be used by itself to read anything. The one thing still worth knowing: anyone with a browser can see and click "Sign in with Google," but the proxy will only ever accept the one allowed email address, so signing in as anyone else simply gets a 401.

Step by stepHow it was built

1Google Cloud — getting API access

  1. Opened a project at console.cloud.google.com and enabled the Google Sheets API for it.
  2. Tried the "normal" approach first — a service account with a downloadable key. Blocked: this Google account's organization has a policy (iam.disableServiceAccountKeyCreation) that forbids it, with no per-project override available.
  3. Switched to OAuth 2.0 instead: configured the OAuth consent screen (External, left in "Testing" mode) and added the account's own email as a Test user — this is what lets Google show the "unverified app" warning instead of a hard block.
  4. Created an OAuth Client ID of type Desktop app and downloaded its JSON — this contains a client_id and client_secret, the app's own identity to Google (not a login credential by itself).

2Trading a one-time login for a permanent refresh token

  1. Ran a small local Node.js script that: opened Google's consent page in a browser, caught the redirect on a temporary local web server (http://127.0.0.1:53682), and exchanged the returned code for tokens via a direct POST to https://oauth2.googleapis.com/token.
  2. Logged in once, as the account that owns the sheets, and approved read-only Sheets access.
  3. The script printed a refresh token — a long-lived credential that lets the proxy silently mint a fresh access token forever, without ever storing a password and without logging in again.
  4. Deleted the script immediately after, since it briefly held the client secret in plain text.

3Writing the proxy itself

  1. A single plain Node.js file (index.js, no framework) using only the built-in http module plus the googleapis package.
  2. On every request it: checks the Authorization: Bearer <token> header matches a secret it holds, builds a Google Sheets client from the OAuth Client ID/Secret + refresh token, then calls the Sheets API.
  3. Two endpoints: ?sheetId=X&sheetName=Y returns one tab's data as CSV text (shaped to match exactly what the old "publish to web" export used to look like, so SheetPulse's parsing code needed zero changes), and ?sheetId=X&action=list returns every tab's name — used to auto-detect the Net Worth workbook's year tabs.

4Hosting it on the Oracle VM

  1. Used a free-tier Oracle Cloud VM already running for another purpose (hostname n8n-server, Ubuntu 24.04).
  2. Installed Node.js and npm, created ~/sheet-proxy, ran npm install googleapis.
  3. Put every secret in one .env file: PORT, AUTH_TOKEN, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_REFRESH_TOKEN (see the token table below).
  4. Wrapped it in a systemd service (sheet-proxy.service) so it starts on boot and restarts on failure. It listens only on 127.0.0.1:3000 — invisible from the internet by itself.
[Unit]
Description=Sheet Proxy
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/sheet-proxy
EnvironmentFile=/home/ubuntu/sheet-proxy/.env
ExecStart=/usr/bin/node /home/ubuntu/sheet-proxy/index.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

sudo systemctl daemon-reload && sudo systemctl enable --now sheet-proxy

5Giving the VM a real name — DuckDNS

Let's Encrypt (the free HTTPS certificate authority Caddy uses) needs a real domain name — it won't issue a certificate for a bare IP address. DuckDNS gives one away for free.

  1. Registered michaelportfolio.duckdns.org and pointed it at the VM's public IP.

6The public face — Caddy

Caddy is the only thing allowed to listen on the real public ports 80 and 443. It automatically requests, installs, and renews an HTTPS certificate, then silently forwards every request to the private Node app on port 3000.

michaelportfolio.duckdns.org {
    reverse_proxy 127.0.0.1:3000
}

7The firewall gotcha — two separate layers

This is the part that actually took the longest to track down: Oracle Cloud has two independent firewalls stacked in front of the same VM, and both have to allow a port before anything reaches it.

  • Layer 1 — Oracle's own "Security List" (cloud-level, configured in the Oracle Console): had a rule for SSH (22) and one custom app (5678), but nothing for 80/443. Added two ingress rules — TCP 80 and TCP 443, source 0.0.0.0/0.
  • Layer 2 — Ubuntu's own iptables (OS-level, invisible from the Oracle Console): a default-reject policy that also only allowed 22 and 5678. Added the same two rules again, directly on the VM, then made them survive a reboot with iptables-persistent.
sudo iptables -I INPUT 7 -p tcp -m state --state NEW -m tcp --dport 80  -j ACCEPT
sudo iptables -I INPUT 7 -p tcp -m state --state NEW -m tcp --dport 443 -j ACCEPT
sudo apt install -y iptables-persistent
sudo netfilter-persistent save

The tell-tale sign it was a firewall (not Caddy, DNS, or the app) was Let's Encrypt's own validation servers failing with "Timeout during connect (likely firewall problem)" in sudo journalctl -u caddy — an external server couldn't even open a TCP connection, which rules out anything running on the VM itself.

8Locking the proxy's front door

  • CORS: the proxy sends Access-Control-Allow-Origin: https://mneyshtadt-stack.github.io and nothing else — a browser will refuse to hand a response to any page loaded from a different address, even if that page somehow had a valid token.
  • Bearer token (superseded in phase 11): at this stage, every request had to carry one shared static secret, or the proxy replied 401 Unauthorized.
  • Un-published the sheets: turned off "Publish to web" for both workbooks in Google Sheets. The old public CSV links now redirect to a Google login page instead of leaking data — confirmed by testing the live old SheetPulse afterward and watching it fail to load.

9Updating SheetPulse

  • Every fetch() to an old "publish to web" CSV URL was replaced with a call to the proxy, carrying the bearer token as a header.
  • The old trick of scraping a sheet's public pubhtml page (to auto-discover the Net Worth workbook's year tabs) was replaced by the proxy's own ?action=list endpoint.
  • The old "paste your own published CSV URL" Settings panel was removed — it no longer makes sense once the backend is one fixed, token-gated server.

10Shipping changes — no git installed here

This machine has no git or gh CLI. Instead, deploy-to-github.ps1 pushes straight through GitHub's REST API:

  1. Reads a fine-grained GitHub Personal Access Token from a file kept outside the OneDrive-synced folder (so it never gets uploaded anywhere by accident).
  2. Reads the local SheetPulse file, stamps a fresh build ID into it (used by an in-page check that force-refreshes any tab still showing an older version).
  3. Pushes the new content directly to index.html in the repo with one authenticated PUT request — no local clone, no commit history to manage by hand.

11Real login: Google Sign-In (SSO)

The proxy's bearer token and SheetPulse's own client-side password screen were both still standing secrets baked into a public page. This phase replaces both with a real, per-request Google identity check.

  1. Created a second OAuth client in the same Google Cloud project, type Web application this time (not Desktop), with Authorized JavaScript origins set to the GitHub Pages address. Its Client ID is meant to be public — unlike a Desktop client's secret, it's designed to be embedded in browser-side code.
  2. Added Google Identity Services (accounts.google.com/gsi/client) to SheetPulse and replaced the old client-side-only SHA-256 password screen entirely with a "Sign in with Google" button and One Tap prompt.
  3. On sign-in, the browser receives a Google ID token — a short-lived, digitally signed JWT containing the signed-in email, name, and profile picture. Every call to the proxy now sends this token as the bearer credential instead of a static secret.
  4. The proxy verifies that token on every single request using the google-auth-library package's OAuth2Client.verifyIdToken() — checking its signature against Google's own public keys, its audience (the Web Client ID), its expiry, and that its email matches one allowed address. Anyone else's valid Google account gets a clean 401.
  5. Added a small account indicator to SheetPulse's header — the signed-in Google profile picture plus a "Sign out" link, which clears the session and calls google.accounts.id.disableAutoSelect() so a different account can be chosen next time.
  6. Forced the sign-in UI to English regardless of browser language by adding ?hl=en to the Google Identity Services script URL.

12Installable as an app — PWA on Android

SheetPulse was still just a bookmarked web page — every open meant a browser address bar and tabs around the actual content. This phase makes Chrome (and other browsers) treat it as a real installable app, with no extra hosting or app-store step.

  1. Added a web app manifest (manifest.json) describing the app's name, colors, and start URL, with display: standalone so an installed copy opens full-screen with no browser chrome.
  2. Added a minimal service worker (sw.js) with a single no-op fetch listener — it doesn't cache anything or serve offline (SheetPulse always needs a live connection to the proxy anyway), but a registered service worker with a fetch handler is one of Chrome's hard requirements for the actual "Install app" prompt, not just a "Create shortcut" bookmark.
  3. Linked the manifest and registered the service worker from SheetPulse's <head>/body, plus added the usual apple-mobile-web-app-* meta tags and touch icon for iOS Safari's own "Add to Home Screen."
  4. Generated two PNG icons (icon-192.png, icon-512.png) and pushed them to the repo root. Chrome's install prompt stayed greyed out ("This app cannot be installed") until both sizes existed — a 192×192 icon alone satisfies the manifest schema but not Chrome's actual installability check, which also requires a 512×512 icon.
  5. Result: on Android, Chrome now offers a genuine "Install app" action (not just a bookmark shortcut), which places an icon on the home screen that opens SheetPulse full-screen, same as a native app.

13Renaming the project to SheetPulse

The app was renamed from a generic "Portfolio Dashboard" to SheetPulse, with a new bar-chart logo.

  1. Renamed the GitHub repository itself from portfolio-dashboard to SheetPulse. GitHub Pages automatically moved the live site to a new path under the same mneyshtadt-stack.github.io origin — the old /portfolio-dashboard/ URL now 404s, while github.com/mneyshtadt-stack/portfolio-dashboard itself still redirects to the new repo page.
  2. Updated the page's <title>, both on-page headers, and manifest.json's name/short_name to "SheetPulse".
  3. Replaced the app icons (icon-192.png, icon-512.png) with a new dark-navy/teal ascending bar-chart mark, with the "SheetPulse" wordmark underneath.
  4. Added the same bar-chart mark, in a small dark rounded-square badge, inline next to the "SheetPulse" wordmark on both the sign-in screen and the main dashboard header, matching the app icon's own style.
  5. Updated the GitHub repository's own "About" description and website link to match, and renamed the local source file portfolio_dashboard_live.html to SheetPulse.html (with deploy-to-github.ps1 repointed at it).
  6. Nothing else needed reconfiguring: the Google Sign-In client's Authorized JavaScript origin and the proxy's CORS allow-list are both keyed to the origin https://mneyshtadt-stack.github.io only, not the path, so the rename didn't touch either. deploy-to-github.ps1's hardcoded repo name had to be updated to match.
  7. One manual follow-up: anyone who had already installed the old PWA (Android "Add to Home screen") needs to reinstall it from the new URL, since the old shortcut's start_url now points at a dead path.

14A faster way back in: biometric quick-unlock (WebAuthn)

Google Sign-In is the real identity check and stays the source of truth, but re-running its full flow every time got old on a phone. This phase adds WebAuthn (Face ID / Fingerprint) as a per-device shortcut layered on top — never a replacement for Google Sign-In, since a device that has never signed in with Google can't register one.

  1. Added four new proxy endpoints: /webauthn/register-options and /webauthn/register-verify (both require a real, fresh Google ID token — proves you're actually the account owner before a new device's biometric can be added), plus /webauthn/auth-options and /webauthn/auth-verify (public, since these are literally how you get back in).
  2. Registered credentials — a public key and a counter per device, never anything biometric itself — are stored server-side in a flat webauthn-credentials.json file next to the proxy; this app has exactly one allowed user, so a small file does the job of a database.
  3. On successful biometric verification, the proxy mints its own short-lived session token (a JWT signed with a new local secret, SESSION_JWT_SECRET, valid 2 hours) instead of a Google ID token. The data endpoints now accept either a real Google ID token or one of these session tokens — both are verified independently on every request, the same as before.
  4. On the frontend: a "Sign in with Google" success now offers an "Enable Face ID / Fingerprint" link; approving it runs the browser's native WebAuthn registration ceremony and flips a local flag (localStorage) so that device's lock screen offers "Unlock with Face ID / Fingerprint" from then on, instead of (or alongside) the Google button.
  5. Used the raw browser navigator.credentials API directly, with hand-written base64url↔ArrayBuffer helpers, rather than a third-party WebAuthn JS library — the CDN library tried initially turned out to have a runtime incompatibility with this device's Chrome version that a small amount of native code sidesteps entirely.
  6. The installed @simplewebauthn/server npm package had to be pinned to major version 9 — the VM's Node.js (v18.19.1) doesn't meet v10's minimum (Node ≥20), and v9's response shapes for registration/authentication (flat credentialID/credentialPublicKey fields) differ from v10's newer nested shape, which the proxy code accounts for explicitly.

15Testing changes locally before deploying

Every change to SheetPulse.html used to only be testable after it was already pushed live. This phase adds a safe local test loop that exercises everything except biometric unlock, without touching production.

  1. Added http://localhost:8000 as a second Authorized JavaScript origin on the same Web OAuth client used in production — one client can list multiple origins, so this needed no new client and no new Client ID.
  2. The proxy's CORS check changed from one hardcoded allowed origin to a small allow-list (ALLOWED_ORIGINS), echoing back whichever of the two origins a request actually came from — the standard multi-origin CORS pattern. WebAuthn's own relying-party ORIGIN deliberately stays pinned to the production domain only, since a biometric credential is tied to its exact domain by design and genuinely can't be tested from localhost.
  3. TestLocal.bat is the local entry point: it copies SheetPulse.html to TestLocal.html fresh on every run — so the test copy can never silently drift out of sync with the real source — starts a local Python server, and opens http://localhost:8000/TestLocal.html, a URL that's unmistakably not production.
  4. The resulting workflow: edit SheetPulse.html → run TestLocal.bat to check Google Sign-In and live data locally → run deploy-to-github.ps1 once satisfied. TestLocal.html and TestLocal.bat are local-only scratch files, never read by the deploy script and never pushed anywhere.
  5. Added a visible build/content indicator in the header — e.g. Build: 20/09/2026 16:43:31 · Content: a40b197c. Build is the deploy timestamp (BUILD_ID); local files always show "local (not yet deployed)" since they're never stamped. Content is a short SHA-256 fingerprint of the page's own source with the BUILD_ID line blanked out first, so it reflects the actual bytes independent of when something deployed — comparing this hash between TestLocal.html and the live GitHub Pages URL right after deploying proves the deploy pushed exactly what was tested, not just "something recent."

16Intraday log timestamps — matching the project's date convention

  1. The IntradayLogIL/IntradayLogUS tabs are written by Apps Script time-driven triggers (logIntradayValueIL/logIntradayValueUS, running every minute while each market is open), which append one Timestamp + Value row per tick and prune everything from a prior day the first time a new day's row is logged.
  2. A raw Date value written into a cell renders using the spreadsheet's own locale — by default, US-style m/d/yyyy — so both logging functions now explicitly call setNumberFormat('dd/mm/yyyy hh:mm:ss') on the Timestamp cell on every write, keeping the column consistent with dd/mm/yyyy everywhere else in the project regardless of the spreadsheet's own locale setting.
  3. That format change meant the dashboard's own CSV parser (fetchIntradayLogRaw) could no longer rely on JavaScript's native new Date(tsStr), which only reliably understands m/d/yyyy order for slash-separated strings and would otherwise have silently turned every dd/mm/yyyy row into an Invalid Date. A small explicit parser (parseSheetTimestamp) now reads the day/month/year/time components directly off the string instead.
  4. Deploying the frontend's dd/mm/yyyy parser ahead of actually pasting the Apps Script's matching format change briefly broke every intraday chart ("logged 0 points so far today") — the sheet was still writing the old m/d/yyyy default, which the new strict parser misread as an invalid month, producing a date that no longer matched "today." parseSheetTimestamp now self-corrects: whenever the "month" slot it read is out of range (>12) and the "day" slot isn't, it swaps them, so a not-yet-migrated m/d/yyyy cell and a correctly-migrated dd/mm/yyyy cell both parse correctly during the transition.

17Prev. close became a real recorded value, not a live approximation

  1. The Day Change/Prev. close figures were previously back-calculated as totalValue - dayGain, where dayGain summed every holding's own live Day Change (%) from the Tracker sheet. That's only an algebraic approximation of "vs. previous close" — it has no real connection to the calendar-math label shown next to it, and can drift from what the portfolio's value actually was at that instant (confirmed by comparing it against an actual snapshot taken at a known past close: the two didn't match).
  2. Added a LastClose tab, written by a new setLastClose() helper called once a day from inside each logging function's existing close-grace-window branch — the same moment that already captures each market's one definitive closing reading. One row per calendar day (columns Date / TASE market / USA market / USA market$ / USD/ILS Rate), rather than per market, since TASE and USA close at different times and each fills in its own columns on that day's row. USA market$ is the USA segment converted back to USD, only ever written at USA's own close since that's the only place both the USD-denominated total and a matching live rate are available together; USD/ILS Rate (read live from Tracker!Q1) gets overwritten at each write too, ending up as whichever close happened more recently that day. Kept to a rolling window of the last 7 rows (not 7 calendar days) — since the trigger never fires Saturday/Sunday, that's the last 7 actual trading days, spanning more than a calendar week whenever a weekend falls in between, with no duplicate weekend rows. Both markets' close is dated by the Israel calendar day it falls on, which is simple and correct nearly year-round (USA's ~23:00 Israel-time close is still the same Israel day as TASE's ~17:30 close) but can, for a few weeks each year around mismatched US/Israel DST transitions, push USA's close past Israel midnight into the next date — a known, low-impact edge case (worst case: one row misses a value), not treated as a bug worth the complexity of dating each market by its own local calendar instead.
  3. The frontend added fetchLastClose(), run alongside every refresh, populating window.lastCloseIL/window.lastCloseUS (and their real-ish timestamps, window.lastCloseILTs/USTs — reconstructed via approxCloseInstant() from just the day's date plus each market's known close time, since LastClose stores a date, not a full timestamp). It scans rows newest-first and takes each market's own most recent non-blank value independently, since a same-day row can have only one market's column filled in. computeTotals() and splitByMarket() now compute dayGain/gain as totalValue - loggedPrevClose whenever that data is available — a real, reconciled number — falling back to the old summed-%-change approximation only before LastClose has any usable row yet.
  4. The Prev. close date/time label (marketPrevCloseReferenceLabel) now also reads the real persisted timestamp when available, rather than deriving a label purely from calendar math — so the value and its "as of" label are now guaranteed to describe the same actual moment, for the IL, US, and combined views alike.
  5. fetchCombinedIntradayLogRaw had a related bug exposed by TASE and USA opening ~6.5 hours apart: mergeIlUs only emits a combined point once both sides have a value, so the entire stretch before the later-opening market's first log row of the day (e.g. TASE's whole morning, before USA opens at ~16:30 Israel time) was silently dropped from the combined chart, even though the earlier market had real data the whole time. Fixed by prepending a flat synthetic point to whichever side starts later, at the earlier side's own first timestamp — using that market's real LastClose value (window.lastCloseIL/US), and only when that real value is actually available. An initial version fell back to ilBaseline/usBaseline (today's live current total, passed in from the regular Tracker refresh) when LastClose had no data yet — which produced a visible fake dip the moment real data arrived, since a still-forming live number isn't the same thing as "hasn't moved yet today." Removed that fallback entirely: without a real LastClose value, the earlier stretch is left unplotted (matching the pre-fix behavior) rather than fabricating a misleading flat line.

18Staying signed in — session storage and token lifetime

  1. The active session token (pf_idToken — either a raw Google ID token or a WebAuthn-issued one) was stored in sessionStorage, which the browser clears the instant a tab or an installed PWA is closed — meaning every reopen forced a fresh sign-in regardless of how long the token itself would otherwise still be valid for. Moved to localStorage instead, across every read/write site in the page; the existing payload.exp > Date.now()/1000 check on load is what actually governs whether the stored token is still honored, so this only changes how long the browser keeps it around, not how validity is decided.
  2. A Google ID token's own lifetime (~1 hour) is fixed by Google and can't be extended from this side — signing in with Google still means re-authenticating roughly hourly if that's the only credential a device has ever used.
  3. The WebAuthn-issued session token, by contrast, is minted by the proxy itself (jwt.sign({ email }, SESSION_JWT_SECRET, { expiresIn: ... })), so its lifetime is fully within this system's control. Extended from 2 hours to 30 days — a device that's registered a biometric credential now stays signed in for a month before needing Face ID/Fingerprint again, rather than every couple of hours.
  4. Signing out (pfSignOut()) explicitly clears the stored token regardless of which kind it is, so the longer lifetime only affects devices left alone, not an explicit sign-out.
